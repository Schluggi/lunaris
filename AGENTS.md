# AGENTS.md — Context for working on this repo

This file is for AI and human agents working on the project. Please update this section when behavior, architecture, or conventions change materially, so context stays accurate for later sessions.

## Purpose

lunaris is a single Rust binary that sends Frozen USART commands locally (without the Eight Sleep cloud): Prime, SetTargetTemperature left/right, GetTemperatures (`0x41` request, opensleep parity), and optionally Vibration on the Sensor UART (SetAlarm per side). Wire format opensleep ([LiamSnow/opensleep](https://github.com/LiamSnow/opensleep): CRC + `0x7E` framing).

Target hardware: Eight Sleep Pod 4 — the protocol is modeled in code/repos after Pod 3 / opensleep and is experimental on Pod 4; differences (TTY, baud, commands) are possible — `[docs/usart-frozen.md](docs/usart-frozen.md)` (Frozen), `[docs/usart-sensor.md](docs/usart-sensor.md)` (Sensor vibration / capacitance).

Deploy target: Pod OS is Linux aarch64 (e.g. “Eight Layer”, `uname -m` → `aarch64`). GitHub releases build `aarch64-unknown-linux-musl` (static musl via `cargo zigbuild`) so the binary does not depend on the Pod’s glibc version — cross-building `aarch64-unknown-linux-gnu` on a modern Ubuntu often produces `GLIBC_2.xx not found` on older Pod images. See README and `[.cargo/config.toml](.cargo/config.toml)`. Running native `x86_64` builds on the Pod → `Exec format error`.

MQTT TLS: `rumqttc` 0.25 pulls `rustls` 0.23 with `rustls-webpki` 0.103.x (Web PKI validation on the TLS connection). `ureq` self-update stays `native-tls` + `openssl-sys` vendored. `rumqttc` also depends on `rustls-webpki` ^0.102 for bundled wire data, so `Cargo.lock` may list two `rustls-webpki` versions until `rumqttc` widens that range. Self-update GitHub calls use short `ureq` connect and small-request timeouts (see `[src/self_update.rs](src/self_update.rs)`); on MQTT connect, the initial Internet Access probe and the first HA Update `latest_version` are not awaited before publishing retained `online` (background probe; first poll fetch fills `latest_version`).

`serialport` 4.x is a direct dependency with `default-features = false` (matches tokio-serial; avoids `libudev-sys`) — used for `SerialStream::set_baud_rate` so the Sensor bootloader→firmware baud switch needs no close/reopen (each open of a `ttyS*` can toggle DTR/RTS and reset the MCU).

HA MQTT discovery `device`: `manufacturer` Lunaris; `sw_version` is the lunaris crate semver only (`CARGO_PKG_VERSION`, e.g. `5.1.0`).

| `[src/hrv.rs](src/hrv.rs)`                       | Heart rate (bpm) + HRV (RMSSD, ms) per mattress side from Sensor piezo `0x32` / `0x35` samples: cascaded-biquad heart-band **bandpass (~0.65–1.95 Hz)** + **~450 ms moving-average smoothing** (merges the sub-peaks of each BCG complex into one hump per beat — without it the detector fired on whichever sub-peak won, inflating the RMSSD to 300–700 ms instead of 20–80 ms) in front of sliding-window DC removal + adaptive threshold, pending-peak beat detection with hysteresis, a 500 ms refractory period and a dicrotic gate (a beat candidate within 750 ms of the previous beat must reach 75 % of the max peak height of the last 4 beats — the bandpassed BCG wave carries a smaller secondary/dicrotic wave ~0.5–0.75 s after each systolic peak; without the gate it registered as an extra beat, inflating RMSSD to 200–450 ms and jittering bpm; reliable range ~40–80 bpm, bandpass passes up to ~117), IBI window (max 32) → `mean_bpm` / `rmssd_ms` (RMSSD is computed and logged but not published to MQTT/HA for now — not calibrated yet); lock expires after ~2.5 s without a beat; `ibi_span_ms` feeds the bridge's constant-IBI artifact guard. The window stats run in **f64** — the channels sit at DC ~32740, where an f32 sum-of-squares (one ULP = 32768) would cancel the ±2 LSB BCG variance away and σ would read ~0 (no beat could ever fire). The bandpass needs a 2 s warmup after the tracker starts (its DC-step ringing would otherwise pollute the window for the first ~2 s). The bandpass is what makes the hardware signal usable: the BCG wave is only ±1–2 LSB and without it the detector fired on respiration/drift waves and quantization wobble (bpm ~20–30 % high, RMSSD 200–500 ms). Unit-tested with synthetic signals, including a realistic ±2 LSB / 204 Hz BCG test.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

Standalone operation: `frozen_link` / `sensor_link` replicate opensleep’s continuous MCU handshake and priming so Prime/climate/vibration work without another service (e.g. frankenfirmware) on the same TTY — only one process may own each UART.

Frozen serial: default `/dev/ttyS1` @ 38400 (Pod 4), or `frozenPort` from `/opt/eight/config/machine.json` when present (unless `--serial-device` is passed). Water Tank and Frozen Message MQTT entities are always discovered; inbound Frozen `0x07` parsing drives them via `frozen_link`. Sensor Message is discovered when the Sensor serial opens (MCU `0x07` via `sensor_link`), along with Cover Button Left/Right (dismiss `(N taps)` counts), the Cover Button Vibration Feedback switch (when a cover-button tap event arrives and the switch is ON, the bridge enqueues one `VibrationBatch::Pulses` batch — cancel preamble per the vibration setting + piezo priming + `N` × `SetAlarm` on the tapped side, pattern Single; `sensor_link` paces the pulses by each `SetAlarm` duration + 500 ms so every tap is a distinct short vibration; when the MCU is already armed + piezo setup complete the pulses go out bare — no cancel/priming, no `0xAE` wait — opensleep `CommandScheduler` parity, because re-priming restarts MCU sampling and can ack `SetAlarm` without physical vibration on some Pods; pulse intensity / duration are runtime HA numbers, defaults 100 % / 1 s), Ambient Temperature / Ambient Humidity from `[ambient]` lines on that UART, and the Heart Rate (bpm) sensor fed by the piezo `0x32` / `0x35` sample stream (`src/hrv.rs`; states publish once enough beats are seen and Presence is ON for that side when capacitance presence is available, throttled to 5 s per side; not retained — when nobody is in bed (presence OFF) the state is cleared with an empty payload so HA shows `unknown` ("not in bed" stays distinguishable from "in bed, no reading" for downstream processing); `0.0` is published only when the side is occupied but the no-reading streak persisted 10 s (lock expired or constant-IBI artifact guard), while a single sporadic zero is held back and never lands in HA; the HRV RMSSD is computed and logged but its HA entities are not exposed for now — empty retained discovery payloads remove previously discovered `hrv_rmssd_*` entities; single-side occupancy auto-routes the livelier piezo wire to that side when labels disagree; `--sensor-piezo-swap-lr` for a static swap; Pod 4/5 tick rate derived from the frame ms‑timestamps (~200 Hz — the SetPiezoFreq 500 Hz target would inflate bpm 2.5×; target only as startup fallback, Pod 3 uses the frame `freq`)). Sensor (vibration): default `/dev/ttyS2` (or `sensorPort` from `machine.json` unless `--sensor-device`) @ `921600` with `--pod 4` or `--pod 5` when `--sensor-baud` is omitted; `--pod 3` → `115200`; `--sensor-baud` overrides — missing device node → no vibration buttons and no capacitance presence (runtime open failures are retried in the background by `sensor_link`). When the Sensor UART opens, MQTT discovers presence: before calibration, `--presence-cap-threshold` (default 800, max‑per‑side; HA Presence Cap Threshold number updates at runtime) applies; after Calibrate presence (leave bed empty for the window — default `--presence-calibrate-secs` 10) baselines apply like opensleep (per‑zone average, Δ from `--presence-baseline-delta` default 50 or HA Presence Baseline Delta number, 5 successive frames touching any zone on a half). Successful Calibrate presence recomputes and retained‑publishes Presence Cap Threshold, Presence Baseline Delta, and Presence Baseline Zones (`…/sensor/presence_baseline_zones/state` as JSON `[z0…z5]`) so the broker keeps them across restarts.

HA settings persistence: After MQTT connect, lunaris runs one bootstrap window (~850 ms) while `mqtt_ha_state_bootstrap` is active: subscribed retained `state_topic` traffic repopulates in-memory HA entities — climate left/right mode + setpoint, MQTT light `…/light/led/state` JSON snapshot, vibration number/select/switch states, presence numbers + baseline zones (Sensor UART / presence entities as configured), plus `…/select/led_behavior/state`. Startup then enqueues Frozen `SetTargetTemperature` for both sides so the MCU matches recovered climate, mirrors states to MQTT, applies vibrate/presence publishes, then applies LED behavior: Manual = LED off and only light entity controls it, Status = solid green while lunaris runs, Startup = green for 5s on process start, then off and manual control. Later inbound `state_topic` echoes are ignored so `command` updates stick. `--presence-debug` logs every capacitance `0x33` inference at INFO, WARN every 60 s if no sample reaches occupancy yet, and a once-only Sensor WARN on the first CRC-valid `0x33` rejected by opensleep layout (Pod 4 layout may differ). (raw six zones, uncalibrated `left_max`/`right_max` vs `--presence-cap-threshold`, or calibrated baseline + per-zone debounce) while debugging HA clear. On startup, `sensor_link` probes the Sensor UART at firmware baud first (MCU already in firmware — no bootloader traffic, no port reopen); only a silent probe falls back to the opensleep-style bootloader handshake (38400 Ping + JumpToFirmware, then an in-place `set_baud_rate` switch to firmware baud). The link reconnects automatically (backoff 2 s → 30 s) on port errors or 45 s without a valid RX frame, so a MCU wedged in its bootloader is healed without a restart. Opens hold the serialport exclusive `flock` — if a stale process holds the device (`Unable to acquire exclusive lock on serial port`), lunaris logs a targeted WARN with a `fuser -v` hint and keeps retrying. The session RX task is aborted and awaited on session end so the port/`flock` is released before the next connect. `--sensor-vibrate-no-ack-wait` skips waiting for inbound `0xAE` (for Pods where RX is not opensleep-framed at the chosen baud). Alarm cancel before each vibrate follows the HA Vibration Cancel Preamble switch (default on). Each vibrate sends EnableVibration + piezo setup + SetAlarm (optionally prefixed by cancel `SetAlarm`, matching opensleep). HA discovers MQTT switch Vibration Cancel Preamble (`enabled_by_default`: false; entity_category config).

LED: I²C `/dev/i2c-1`; probe error → no light. With LED enabled, HA discovers an LED Behavior select (`…/select/led_behavior/set|state``, retained): Manual (LED off at boot; control only via MQTT light entity), Status (LED solid green while lunaris runs; light commands ignored), Startup (LED green for 5s on start, then off; manual control via light entity afterwards). On exit (SIGINT / SIGTERM / MQTT loop stop), the LED is turned off.

## Conventions for changes

- Documentation in this repo (`README.md`, `AGENTS.md`, `docs/`): do not use Markdown bold or italic for emphasis; plain wording and backticks for code or paths are enough.
- Git commits (Conventional Commits / semantic-release style): Use [Conventional Commits](https://www.conventionalcommits.org/) so messages work with commitlint and match what semantic-release expects — e.g. `feat:`, `fix:`, `docs:`, `chore:`, `ci:`, `refactor:`, `test:`, `perf:`; breaking changes via `feat!: …` or `feat:` plus a `BREAKING CHANGE:` footer on that commit. This repo does not run the npm semantic-release tool; `[.github/workflows/release.yml](.github/workflows/release.yml)` on push to `main`/`master` publishes only when a commit in the since-tag range has a `feat:` or `fix:` subject (`chore:`, `docs:`, etc. do not trigger a release); bump rules: major only for feat breaking (`feat!:`, or `feat:` + footer), minor for non-breaking `feat:`, patch for `fix:` (including `fix:` with a `BREAKING CHANGE:` footer — still patch). `workflow_dispatch` still runs the release when triggered; bump uses the same since-tag `feat:` / `fix:` / breaking rules as push, with patch when that range has no such subject (forced release without semver commits).
- Language: User-facing text (Home Assistant discovery names, README, `docs/`, CLI help) is English only.
- License: GPL-3.0 (`[LICENSE](LICENSE)`). Code/framing traceable to opensleep → keep attribution/source notices in affected files.
- Scope: Stay focused (no large drive-by refactors). Add new features (TLS, more entities) deliberately and document them.
- New MQTT / Home Assistant entities: Update `README.md` with the new entities (topics, purpose) in the same change as the code — not only `AGENTS.md` / inline discovery.
- README style: Keep README edits minimally invasive and only document what is necessary. Prefer simple, plain wording and avoid overly technical language.
- Tests: Unit-test critical logic (CRC, frame bytes); CI (`[.github/workflows/ci.yml](.github/workflows/ci.yml)`: `fmt`, `test`, `clippy`; separate job aarch64 `release` cross-build) runs on pull requests only. On push to `main`/`master`, `[release.yml](.github/workflows/release.yml)` is workflow-level path-filtered to changes under `src/`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, or `.cargo/` (documentation-only merges do not start the workflow); it publishes only if there is a semver-relevant commit after the last tag (`fix:`, `feat:`, or breaking change via `BREAKING CHANGE:` / `!`); otherwise it succeeds without publishing. The `chore(release):` version bump touches `Cargo.toml` and thus can still enqueue a run that skips the release job via the existing message guard. `workflow_dispatch` always runs the full release job (same bump logic as push; patch fallback). When a release runs: version bump in `Cargo.toml` follows semver rules (major/minor/patch by commit type), then Git tag `v*.*.*`, GitHub Release with aarch64 Linux binary (+ `SHA256SUMS`); release notes group commits from the previous tag to the new tag by Conventional Commit type (no merge commits, no `chore(release):` bump), emoji section headings; newest-first within each section; not GitHub’s PR-based auto notes.
- Toolchain: `[rust-toolchain.toml](rust-toolchain.toml)` pins the compiler (currently 1.99.x) and declares `aarch64-unknown-linux-musl` in `targets` so `rustup` installs the musl stdlib for the same channel the repo uses (avoids E0463 when a workflow step installed the target only on an older toolchain). `[Cargo.toml](Cargo.toml)` sets `package.rust-version` to match. Dependencies use normal semver ranges (no `clap` / `url` MSRV pins). Self-update enables `openssl-sys/vendored` (compile OpenSSL via `openssl-src`; needs a C toolchain / `perl` for the OpenSSL build script).

## Commands

After any Rust source edit, run `cargo fmt --check` (or `cargo fmt` to apply). CI fails if formatting disagrees with rustfmt — same check as `cargo fmt --check`.

```bash
cargo fmt --check
cargo test
cargo clippy --all-targets --all-features -- -D warnings
cargo build --release
# Pod / aarch64 (static musl — matches CI releases; Zig on PATH; cargo-zigbuild 0.23.4 --locked; Rust per rust-toolchain.toml):
# rustup target add aarch64-unknown-linux-musl
# cargo install cargo-zigbuild --version 0.23.4 --locked
# cargo zigbuild --release --target aarch64-unknown-linux-musl
```

cargo-zigbuild must be at least 0.23.4: since Rust 1.98, rustc passes `-Wl,--fix-cortex-a53-843419` when linking `aarch64-unknown-linux-musl` (a GNU-ld-only Cortex-A53 erratum workaround), and `zig cc` rejects that linker arg with `unsupported linker arg`. cargo-zigbuild 0.23.4 strips the flag before invoking zig (rust-lang/rust#155453); older versions fail at the final link.

Logging: `RUST_LOG`, plus `--log-level` (see `--help`).
